Observations:•Whichever instruction we are executing, it must go through these five phases. Such a time phase is usually a single clock cycle.•Typically each phase uses only some portions of the CPU.•If we wait for the completion of an instruction, before we start the opcode fetch of the next instruction, much of the CPU is idle.•This is not very efficient, since most of the CPU is not being used, most of the time.

Pipelining•An alternative approach is to “pipeline” the CPU. •In a pipelined CPU design, the internal architecture is organised in such a manner, that we can execute separate phases of consecutive instructions concurrently.•Therefore, the result of an instruction appears at the end of every time phase.•For this example, this CPU on average completes instructions five times faster than the previous example.

Pipeline Latency•While each instruction still takes 5 time phases to complete, since consecutive instructions overlap, results are produced once per time phase.•The time delay of five time phases in this example is termed the “pipeline latency” or “latency” of the CPU.•If the CPU has stalled for whatever reason (e.g. cache miss), one latency period must elapse before the CPU can start producing results again.

=== PAGE 22 ===
www.infotech.monash.edu
22
Pipeline Throughput
•The “throughput” of the non-pipelined CPU was one instruction per 5 time phases.•The “throughput” of the pipelined CPU is one instruction per time phase, i.e. 5 X faster.•In practical terms, this means the pipelined variant of this CPU can execute programs around 5 X faster than the non-pipelined variant.•This gain in performance is a result of all portions of the CPU being busy all of the time.

=== PAGE 23 ===
www.infotech.monash.edu
23
Pipeline Stalls
•A “pipeline stall” can arise whenever some portion of the CPU must wait for another portion of the CPU to complete its work.•An example is a cache miss in a CPU with a big difference in speed between the CPU and main memory. •While the CPU is waiting for an opcode fetch to complete (i.e. the main memory to respond and return the fetched opcode), the preceding instructions in the pipeline are completed.

=== PAGE 24 ===
www.infotech.monash.edu
24
Pipeline StallsOnce the stall has finished, it will take at least one latency period before the CPU starts completing instructions, phase after phase.Stalls are to be avoided at any cost!Stalls may arise for various reasons:A.Poor CPU design (e.g. Panasonic MN10501 CPU)B.Data Hazards.C.Unresolved Conditional Branches.D.Cache and TLB misses.

=== PAGE 25 ===
www.infotech.monash.edu
25
Pipeline Stages
•When designing a pipelined CPU, it is common practice to divide the CPU internally into “pipeline stages”, each of which contains all the components required to perform the tasks required in a particular time phase of instruction execution.•Each stage of the pipeline must be capable of completing its work in the same amount of time as every other stage.

=== PAGE 26 ===
www.infotech.monash.edu
26
Pipeline StagesNB: if any stage takes longer than its peers to complete its work, then the whole pipeline must be slowed down to the speed of the slowest component in the pipeline.Therefore design choices in one area of the CPU will affect other areas.

=== PAGE 27 ===
www.infotech.monash.edu

Data Hazards•Consider the effects of trying to execute an instruction using the results from an immediately preceding instruction.•In many CPU designs, the result from instruction “N” may not be ready when instruction “N + 1” needs to use it.•How should this be handled ?A.Make sure the compiler or programmer never tries to do this (e.g. MIPS R2000/3000, XSPIM hides it).B.Stall the pipeline until the result is ready for use.C.Forward the result.

Data Forwarding•Stalling the pipeline incurs a loss in performance, since all following instructions are delayed.•An alternative technique which may be used is "data forwarding".•Rather than stall the pipeline, we route the result of the preceding instruction directly from the ALU, bypassing the store into the intended destination register.

Conditional Branches•Another situation which can cause difficulties in a pipelined CPU is a conditional branch instruction.•A conditional branch must always wait until an earlier instruction, which determines the direction of the branch, has completed.•If we wait for the completion of a conditional branch instruction, before we start the opcode fetch of the next instruction, the pipeline will be stalled.

=== PAGE 35 ===
www.infotech.monash.edu
35
Conditional BranchesUntil the CPU knows the outcome of the branch, it does not know where in the program it should be fetching the instructions following the branch from.How should we best handle such instructions without suffering a big loss in performance?

=== PAGE 36 ===
www.infotech.monash.edu
36
Conditional Branches• Solutions exist for this problem: 1.Stall the pipeline until the branch is resolved.2.As above, but store the “branch target” in a special cache, and next time use the cached value to determine where to fetch the instructions following the conditional branch from. NB: A cache is a fast but small memory for storing frequently used data or instructions, in this instance the address of the “branch target” NB: if the branch does not take the “cached” direction, the pipeline must be restarted again.

Parallelism•A pipelined CPU exploits a form of parallelism, in that consecutive instructions are processed in parallel, but mutually overlapped.•Processing instructions in parallel is only possible when there are no mutual dependencies between operands in these instructions.•The dependency between the operands in two consecutive instructions, in the earlier example, required a pipeline stall or data forwarding to resolve.

=== PAGE 38 ===
www.infotech.monash.edu

ParallelismCan parallelism be further exploited in a CPU to improve performance ?The answer is yes, providing that we can resolve dependencies between operands!Superscalar and Very Large Instruction Word (VLIW) CPUs exploit “Instruction Level Parallelism (ILP)”.

=== PAGE 42 ===

What is Instruction Level Parallelism?•Where multiple instructions do not depend upon the results of each other, these instructions can be executed in parallel, i.e. concurrently.•The property of not being mutually dependent upon each other’s results is termed Instruction Level Parallelism or ILP.•The level of ILP in any piece of code depends on the algorithm being executed, and how the compiler organises the instructions.•How can we exploit ILP?

=== PAGE 43 ===
www.infotech.monash.edu
43
Superscalar Processing•One technique for improving CPU performance by exploiting ILP is “superscalar processing”.•Superscalar techniques first appeared in mainframes and supercomputers during the 1960s, now they are used in most modern CPUs.•A superscalar CPU employs more than one pipeline/ALU, so it can execute more than one instruction concurrently, should the opportunity arise to do so.•Caveat? ILP must be present for superscalar processing to occur – no ILP ⇒ no parallel speedup!

Superscalar Processing
•In a superscalar CPU it is customary to call the ALU hardware an Execution Unit (EU).•There is no requirement for the EUs to be identical, in most superscalar CPUs there are several types of EU, e.g. Integer/Logical, Address Arithmetic and Floating Point.•The performance gain over a CPU with a single EU can as little as 50%, in practice a 200% to 500% improvement is common.

Superscalar ProcessingTo achieve maximum performance gain it is necessary to efficiently detect ILP in the executable code.Detecting ILP requires that the CPU analyse the instruction stream to find opportunities to execute instructions in parallel.Up to 25-30% of the hardware in a contemporary superscalar CPU may be used for this purpose.

Performance Limitations in SSP•Several factors can impair the performance of a superscalar CPU:A.Data (Output) Dependency.B.Procedural Dependency.C.Resource Conflicts.D.Anti-dependency.

Data DependencyEssentially the same type of problem as a “data hazard” seen in a pipeline.The result from instruction "N" may not be ready when instruction "N + 1" needs to use it.Handled by stalling the pipeline until the result is available, or by result forwarding where possible.Many data dependencies are inherent in the program being executed and cannot be avoided.

Resource Conflicts
•Resource conflicts arise when more than one instruction needs to use an EU, register or bus. •This is essentially a “deadlock” situation since one or more instructions must wait for the resource to complete its work.•Resource conflicts can be removed by adding more registers, busses and EUs into the CPU. •This incurs much additional cost in hardware.

Procedural Dependency
•The procedural dependency problem is essentially the same  problem seen in a pipeline due to a conditional branch.•Until the result of the branch is known, the pipelines are stalled. •In a superscalar CPU, many more instructions are delayed, in comparison with a single pipeline, therefore the performance loss is much greater.

Speculative ExecutionProcedural dependency can be handled by “speculative execution”, where the CPU calculates both possible instruction streams following the branch and then throws one away, once the outcome of the branch is known.Speculative execution is very expensive in hardware, since two threads of execution must be followed to get one thread of results.Early Example: Intel Pentium Pro/II/III CPU.

=== PAGE 74 ===
www.infotech.monash.edu

Anti-Dependency
•Anti-dependency arises when an instruction overwrites the source operand for a preceding instruction.•This is not a problem in a pipelined CPU since the instructions are executed in their proper order.•In a superscalar CPU, which may use “out of order” execution, anti-dependency prevents the execution of the later instruction until the source operand has been used.

=== PAGE 75 ===
www.infotech.monash.edu
75
Out of Order Execution (OOE)
•If no dependency exists between instructions, there is no requirement for these instructions to be executed in the CPU in the same order as they appear in memory.•OOE is frequently used since it allows instructions with no dependencies to be executed when “convenient” opportunities arise between instructions with dependencies.•OOE allows optimal use of a superscalar CPU.•Instruction results are usually written in order.

• In a pipelined CPU design, the internal architecture

separate phases of consecutive instructions 
concurrently.

end of every time phase.

instructions five times faster than the previous

Pipeline Latency
• While each instruction still takes 5 time phases to 
complete, since consecutive instructions overlap, 
results are produced once per time phase.
• The time delay of five time phases in this example is 
termed the “pipeline latency” or “latency” of the 
CPU.
• If the CPU has stalled for whatever reason (e.g. 
cache miss), one latency period must elapse before 
the CPU can start producing results again.

=== PAGE 88 ===
www.infotech.monash.edu

Pipeline Throughput
• The “throughput” of the non-pipelined CPU was one 
instruction per 5 time phases.
• The “throughput” of the pipelined CPU is one 
instruction per time phase, i.e. 5 X faster.
• In practical terms, this means the pipelined variant 
of this CPU can execute programs around 5 X faster 
than the non-pipelined variant.
• This gain in performance is a result of all portions 
of the CPU being busy all of the time.

Pipeline Stalls
• A “pipeline stall” can arise whenever some portion 
of the CPU must wait for another portion of the CPU 
to complete its work.
• An example is a cache miss in a CPU with a big 
difference in speed between the CPU and main 
memory. 
• While the CPU is waiting for an opcode fetch to 
complete (i.e. the main memory to respond and 
return the fetched opcode), the preceding 
instructions in the pipeline are completed.

 Once the stall has finished, it will generally take at

 Stalls may arise for various reasons:

Data Forwarding
• Stalling the pipeline incurs a loss in performance, 
since all following instructions are delayed.
• An alternative technique which may be used is "data

Data Dependency
 Essentially the same type of problem as a “data 
hazard” seen in a pipeline.
 The result from instruction "N" may not be ready 
when instruction "N + 1" needs to use it.
 Handled by stalling the pipeline until the result is 
available, or by result forwarding where possible.
 Many data dependencies are inherent in the 
program being executed and cannot be avoided.

=== PAGE 115 ===
www.infotech.monash.edu

Resource Conflicts
• Resource conflicts arise when more than one 
instruction needs to use an EU, register or bus. 
• This is essentially a “deadlock” situation since 
one or more instructions must wait for the 
resource to complete its work.
• Resource conflicts can be removed by adding 
more registers, busses and EUs into the CPU. 
• This incurs much additional cost in hardware.

=== PAGE 116 ===
www.infotech.monash.edu

Procedural Dependency
• The procedural dependency problem is 
essentially the same  problem seen in a pipeline 
due to a conditional branch.
• Until the result of the branch is known, the 
pipelines are stalled. 
• In a superscalar CPU, many more instructions 
are delayed, in comparison with a single 
pipeline, therefore the performance loss is much 
greater.

=== PAGE 117 ===
www.infotech.monash.edu

Anti-Dependency
• Anti-dependency arises when an instruction 
overwrites the source operand for a preceding 
instruction.
• This is not a problem in a pipelined CPU since the 
instructions are executed in their proper order.
• In a superscalar CPU, which may use “out of 
order” execution, anti-dependency prevents the 
execution of the later instruction until the source 
operand has been used.

=== PAGE 118 ===

Out of Order Execution (OOE)
• If no dependency exists between instructions, 
there is no requirement for these instructions to 
be executed in the CPU in the same order as they 
appear in memory.
• OOE is frequently used since it allows 
instructions with no dependencies to be 
executed when “convenient” opportunities arise 
between instructions with dependencies.
• OOE allows optimal use of a superscalar CPU.
• Instruction results are usually written in order.

▪ Condition variables
– Synchronization primitives allowing threads to wait for a specific condition 
before continuing execution. 
– Commonly used in multithreaded programs to coordinate communication 
between threads and avoid unnecessary busy waiting.
▪ Used together with mutexes to safely synchronize access to shared resources.
▪ Idea: Allows one thread to wait while another thread signals that a task or 
resource is ready.
▪ Application: Producer-consumer, sender-receiver, and task scheduling 
scenarios.
Condition Variables 

=== PAGE 130 ===
8
▪ Semaphores and Condition Variables share the same core operations (wait() 
and signal())to provide mutual exclusion. However, they differ in how they 
manage waiting threads:
– Semaphores are strictly conditioned on an internal semaphore count 
(blocking when zero, proceeding when non-zero).
– Condition Variables are associated with an arbitrary logical condition 
defined by the programmer.
▪ Threads sleep on a condition variable until signaled. Once awakened, the 
thread checks the custom condition: if met, it proceeds; otherwise, it is directed 
back to waiting.
Semaphores vs. Condition Variables

Problem 1: Lost Signals 
▪ Condition variables have no memory. If a signal is sent when no thread is 
waiting, the signal is permanently "lost."
▪ A thread that blindly waits without checking the condition first may deadlock, 
waiting forever for a signal that already happened.
▪ Always test the condition before deciding to wait.

▪ To maximize performance on multiprocessor systems, threads can occasionally 
wake up without actually receiving a signal.
▪ Always re-test the condition immediately after waking up. If it was a spurious 
wakeup, the thread should go right back to sleeping.

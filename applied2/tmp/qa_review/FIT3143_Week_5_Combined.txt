=== PAGE 70 ===
15
▪Typical processors, pipelined or superscalar, do not perform 
well on vector arithmetic since they do not exploit the  
properties of vectors.
▪Vector arithmetic involves the repeated execution of the 
same operation on consecutive elements of a vector.
▪This is the SIMD model of execution
▪Conventional processors incur an opcode fetch, operand 
load and decode delay for every element in the vector - very 
inefficient
Vector Processing

=== PAGE 71 ===
16
▪How can we optimise an architecture for vector arithmetic ?
▪We can use an instruction set for vector operations: e.g. 
Add vector operands of size N, V3 and V2, and put the 
result into V1.
ADD N, V1, V2, V3
▪A vector operand may be a pointer to an array in memory, 
or a register.
Vector Processing

=== PAGE 72 ===
17
▪Using vector operations we remove the overheads of N-1 
opcode fetches, decodes and operand loads.
▪Because the same operation is repeated N times, we can 
operate a pipeline for N consecutive cycles with no stalls, 
which is very efficient.
▪By using multiple execution units, we can achieve stall free 
superscalar operation, which is also very efficient.

19
▪The technique of “chaining” is frequently used in vector 
processing architectures.
▪Because the loading of an N element vector  into a vector 
register requires N consecutive loads from memory, it is 
slow.
▪By arranging the use of the vector registers properly, in a 3 
operand vector architecture, and using at least 4 vector 
registers, it is possible to load one vector operand while two 
others are being read into the EU and written into another

=== PAGE 100 ===

M P I = Message Passing Interface 
MPI is a specification for the developers and users of message passing libraries. By 
itself, it is NOT a library - but rather the specification of what such a library should 
be. 
Simply stated, the goal of the Message Passing Interface is to provide a widely 
used standard for writing message passing programs. The interface attempts to be 
▪ practical 
▪ portable 
▪ efficient 
▪ flexible 
What is MPI

=== PAGE 101 ===
5
▪ Standardization - Supported on all major platforms and also many specialised 
HPC systems. (Practically has replaced all previous message passing libraries) 
▪ Portability - Minimum (to none) need to modify your source code when you port 
your application to a different platform compliant with MPI (standard). 
▪ Performance Opportunities - Vendor implementations can exploit native hardware 
features to optimize performance. 
▪ Functionality - About 128 functions/routines in MPI 1.3, finalised in 2008. By 2026, 
MPI has reached 5.0. 
▪ Availability - A variety of implementations on the standard are available (vendor 
and public domain implementations). 
(For Applied/Lab assessment: OpenMPI library implementations)
Reasons for Using MPI

=== PAGE 102 ===

▪ MPI supports almost any popular distributed memory parallel programming model.
▪ MPI can also be used to implement/support many shared memory models. 
▪ Hardware platforms: 
– Distributed Memory: Primarily targeted for distributed memory systems. 
– Shared Memory: As shared memory systems became more popular (SMP / 
NUMA architectures), MPI implementations for these platforms appeared. 
– Hybrid: MPI supports most common hybrid architecture (massively parallel 
machines, SMP clusters, workstation clusters and heterogeneous networks,  
etc).

General Concepts
▪ Types of Point-to-Point Operations: 
– Message passing between two different MPI tasks (process). One task is performing a send 
operation and the other task is performing a matching receive operation. 
– Different types of send and receive routines for different purposes:
▪ Synchronous
▪ Blocking 
▪ Non-blocking 
▪ Buffered 
▪ Routines combining send & receive 
– MPI also provides several routines associated with send - receive operations, such as those 
used to wait for a message's arrival or probe to find out if a message has arrived. 
Point to Point (P2P) Communication

=== PAGE 119 ===
23
Buffering: 
In a perfect world, every send operation should be 
perfectly synchronized with its matching receive. In 
practice, this is rarely the case. The MPI implementation 
must be able to handle tasks that are out of sync. 
Consider the following two cases: 
▪ A send operation occurs 5 seconds before the 
receive is ready - where the message is stored?
 
▪ Multiple sends arrive at the same receiving task 
which can only accept one send at a time - what 
happens to the messages that are "backing up"? 
P2P general concepts
The MPI implementation (not the MPI standard) 
decides what happens to the data in these types 
of cases. Typically, a system buffer area is 
reserved to hold data in transit. 

=== PAGE 120 ===
24
System buffer space is: 
▪ Managed entirely by the MPI library implementation
▪ A finite resource that can be easily exhausted 
▪ Often mysterious and not well documented 
▪ May exist on the sending side, the receiving side, or both 
▪ Can be used to improve program performance because it allows send - receive 
operations to be asynchronous. 
▪ User managed address space (e.g., storing your program variables) is called 
the application buffer. 
P2P general concepts

=== PAGE 121 ===
25
Blocking vs. Non-blocking: 
▪ Most of the MPI point-to-point routines can be used in either blocking or non-blocking mode. 
▪ Blocking: 
– A blocking send routine will only "return" after it is safe to modify the application buffer (your 
send data) for reuse. “Safe” does not imply that the data was actually received. Data may still be 
sitting in system buffer waiting to be sent. 
– Synchronous blocking send: Block until handshake occurs with the receive task (process). 
– Asynchronous blocking send: Block until data is copied to the system buffer, which is used to 
hold the data for the “eventual” delivery. 
– Blocking receive: Blocks until after the data has arrived and is ready for use by the program.
▪ Your parallel design will determine whether you should use blocking/non-block functions. Deadlocks, 
computation errors, or failing to speed-up the program are common symptoms of using the wrong 
functions with the wrong parallel design. 
P2P general concepts

=== PAGE 122 ===
26
▪ Non-blocking: 
– Non-blocking send and receive routines will return “almost” immediately. 
– They do not wait for any communication events to complete, such as message 
copying from user memory to system buffer space or the actual arrival of message. 
– Non-blocking operations simply "request" the MPI library to perform the operation.
– Corollary: It is unsafe to modify the application buffer (your variable space) until you 
know the requested operation has been completed. A series of "waiting"/"probing" 
routines are designed for checking whether operations have been completed. 
– Non-blocking communications are primarily used to overlap computation with 
communication and exploit possible performance gains
P2P general concepts

=== PAGE 123 ===
27
Order:
– MPI guarantees that messages are “ordered” and will not overtake 
each other. 
– If a sender sends two messages (Message 1 and Message 2) in 
succession to the same destination, and both match the same 
receive, the receive operation will receive Message 1 before 
Message 2. 
– If a receiver posts two receives (Receive 1 and Receive 2), in 
succession, and both are looking for the same message, Receive 
1 will receive the message before Receive 2. 
– Order rules do not apply if there are multiple threads participating 
in the communication operations. 
P2P general concepts

– MPI does not guarantee fairness
– The programmer has responsibility to prevent operation/process 
starvation. 
– Often depends on how processes are scheduled in the underlying 
Operating System.

Collective Communication

=== PAGE 148 ===

All or None: 
▪ Collective communication involve all processes in the scope of a communicator. 
▪ Programmer's responsibility to ensure all processes within a communicator are 
correctly participating in any collective operations. 
General types of collective operations: 
▪ Synchronization: processes wait until all members of the group have reached the 
synchronization point. 
▪ Data Movement: broadcast, scatter/gather, all to all. 
▪ Collective Computation (e.g., reductions): one member of the group collects data 
from the other members and performs an operation (e.g., min, max, add, multiply) 
on that data.
